# AI & Developer Instructions: how the 7 of us work on this project

> **Any AI model (Claude, Copilot, Cursor, ChatGPT...) working on this repository MUST read and obey this file before touching any code.**
> If a rule here conflicts with what the user asks, tell the user about the conflict and ask. Do not silently break a rule.

Project: **Sourcing & Tender Management System** for a cosmetics company. 7 developers work in parallel on one repository.
Stack: **ASP.NET Core 10 MVC + Entity Framework Core + SQL Server + ASP.NET Core Identity + Bootstrap**.
Goal of this file: **one unified way of working, so nobody ever creates a merge conflict.**

---

## 1. The golden rules (read these twice)

1. **NEVER touch another person's code.** Only edit the files that belong to the task you were given (see section 4, "who owns what").
2. **Only ADD. Do not rewrite.** Do not rename, move, reformat, "clean up" or "improve" files you did not create. No mass "organize usings", no `dotnet format`, no find-and-replace across the solution.
3. **Keep it simple. No strange or advanced classes.** Forbidden unless the lead approves in writing: generic repositories, Unit of Work, MediatR, CQRS, AutoMapper, custom base controllers, custom attributes, custom middleware, source generators, reflection tricks, new design-pattern layers. A normal controller, a simple ViewModel, a simple entity and (only if needed) a simple service class are enough.
4. **Shared files are read-only for you** (section 5). If your task needs a change there, STOP and tell the user: "this needs the lead".
5. **Do not add NuGet packages** or edit `*.csproj` without asking the lead. The project file is shared by everyone.
6. **Never commit secrets or machine files** (`.env`, `bin/`, `obj/`, `.vs/`, uploaded files). See section 8.
7. **When unsure, ask the user.** A question is cheaper than a conflict.

### Data vs Models: the difference in one minute

* **Entity** (in `Data/Entities`) = a row in the database. Example: `Tender` has `Id`, `Title`, `Status`... EF Core turns it into the `Tenders` table.
* **ViewModel** (in `Areas/<Role>/Models`) = what one web page needs. Example: `CreateTenderViewModel` has only the fields of the "Create tender" form, with `[Required]`, `[StringLength]` attributes.
* The controller converts between them: form -> ViewModel -> Entity -> `SaveChanges()`; and Entity -> ViewModel -> View.
* Never pass an Entity straight to a form (security and validation problems). Never put a ViewModel in `Data/`.

## 3. The unified way to build ANY task

Follow these steps in this order, every time, whatever the task is.

1. **Know who you work for.** Ask the user "who are you?" if the task does not say. Your files and tasks are in section 4 and in `TASKS.md`.
2. **Sync first.** `git checkout main` -> `git pull` -> `git checkout -b feature/<area>-<what>` (example: `feature/sourcing-tender-create`).
3. **Read before writing.** Look at the existing placeholder controller and view in your area. Follow the same style. Look at `docs-site/database/schema.sql` (or open `docs-site/SourcingTender-Docs.html`) for table and column names. Do not invent your own names.
4. **Entities already exist.** The lead generated all 29 entity classes from the schema (`Data/Entities/<Feature>/<Name>.cs`), their `DbSet`s (`Data/DbSets/ApplicationDbContext.<Feature>.cs`) and the baseline migrations. Find yours, read it, use it. You may add a missing property or `[Attribute]` to an entity **you own** (then you need a migration, section 10). You may not rename or delete columns without the lead. Only if the feature truly needs a NEW table: create a new class in `Data/Entities/<Feature>/` and its `DbSet<T>` in YOUR DbSets file. Never edit `ApplicationDbContext.cs`.
5. **ViewModel.** Create it in `Areas/<Role>/Models/`. Name: `<Action><Thing>ViewModel`. Put validation attributes on it (`[Required]`, `[StringLength]`, `[Range]`, `[EmailAddress]`, `[Display(Name = "...")]`).
6. **Controller action.** Put it in your area's controller (section 6 explains how to avoid conflicts). Keep it short:
   * `GET` action loads data and returns `View(model)`.
   * `POST` action: `if (!ModelState.IsValid) return View(model);` -> save -> `RedirectToAction(...)`.
   * Use `[ValidateAntiForgeryToken]` on every POST.
   * Inject `ApplicationDbContext` through the constructor and use it directly. No repository layer.
7. **View.** Fill the existing placeholder view (or create `Views/<Controller>/<Action>.cshtml`). Use Bootstrap classes and the palette (section 9). Server-side validation messages with `asp-validation-for`.
8. **Schema change (only if you changed an entity).** Do NOT create a migration. Push your branch with just the entity change and tell Wadea; he creates the migration (section 10).
9. **Test.** `dotnet build`, then `dotnet run --launch-profile https` and open the page. Check the happy path and one error path.
10. **Commit and push your branch.** Small commits, clear message (section 11). Open a pull request. Never push to `main`.

## 6. How to work in the same controller without conflicts

Best case: **one controller = one person.** Each area already belongs to one owner, so normally you do not share a controller.

When two people really must add actions to the same controller (rare):

1. **Do not change any existing line.** Add your new action at the **very end** of the class, after a blank line, wrapped in your own region:
   ```csharp
   #region Dev4 - Tender suppliers
   // your actions here
   #endregion
   ```
   Two people adding at the very end can still collide, so prefer option 2.
2. **Better: make the controller `partial` and put your actions in your own file.** Example: `TendersController.cs` (owner) and `TendersController.Suppliers.cs` (you):
   ```csharp
   namespace TenderSystem.Areas.Sourcing.Controllers;

   public partial class TendersController
   {
       public IActionResult Suppliers() => View();
   }
   ```
   The owner adds the word `partial` to the original class line once (one-word change). After that nobody edits the same file again.
3. **Views:** never share a view file. One action = one `.cshtml` file = one author.
4. **Same rule for any other class or file:** if two people need the same file, split it into two files instead of editing one.

## 7. Services: keep it simple

* For normal CRUD (list, create, edit, details) put the code **directly in the controller** using `ApplicationDbContext`. That is fine and expected.
* Create a service class **only** when the same logic is used by two or more controllers, or the logic is long and hard to read (more than about 50 lines).
* A service is a normal class: `Services/<Feature>/TenderService.cs` with plain methods. An interface is optional. No base classes, no generics.
* Register it in **your own** `IFeatureModule` class (never in `Program.cs`):
  ```csharp
  // Services/Tenders/TendersModule.cs
  namespace TenderSystem.Services.Tenders;

  public class TendersModule : IFeatureModule
  {
      public void Register(IServiceCollection services, IConfiguration configuration)
      {
          services.AddScoped<TenderService>();
      }
  }
  ```
  `Program.cs` finds every `IFeatureModule` automatically.

## 8. `.env`, `.env.example` and `.gitignore`

### What is `.env`?
A small text file with **settings that are different per machine or secret**: the SQL Server connection string, Ollama address, face-encryption key, email password, WebAuthn host. It is read at startup by `Program.cs` (`Env.TraversePath().Load()`), so the values appear as environment variables. It lives next to `Program.cs`.

* `.env` is **never committed** (it is in `.gitignore`). Each developer has their own copy.
* `.env.example` **is committed**. It lists every key with a safe example value and NO real secret.
* First time: copy `.env.example` to `.env` and edit your values.

### Adding a new setting
1. Add the key to **`.env.example`** at the end, under a comment with your feature name. Never put a real secret in it.
2. Tell the team to add the same key to their `.env`.
3. Read it in your code with `Env.GetString("MY_KEY", "default")` (`using DotNetEnv;`). Do not hard-code secrets, URLs or passwords in C# or in `appsettings.json`.
4. Do not edit `AppOptions.cs` (lead file) just to read one value.

### Sending email
Use `EmailService` (Wadea, `Services/Email/`). Never write your own SMTP code.
```csharp
// inject EmailService in your controller or service constructor
await _email.SendAsync(user.Email!, "Welcome", EmailTemplates.Welcome(user.FullName, user.Email!, tempPassword, _email.AbsoluteUrl("/Account/Login")));
```
* Ready templates: `Welcome`, `SupplierApproved`, `SupplierRejected`, `SupplierSuspended`, `PasswordReset`, `Notification`. Need a new email? Ask Wadea to add a template method.
* It never throws; it returns `false` if sending failed. Do not let a failed email stop your action.
* `SMTP_ENABLED=false` (default): nothing is sent, in Development the email is saved as `App_Data/emails/*.html` (open it in a browser). To test real sending set `SMTP_ENABLED=true` and the `SMTP_*` keys (see `.env.example`). Check your settings at `/dev/send-test-email?to=you@example.com` (Development only).

### What is `.gitignore`?
A file at the **repo root** that tells git which files to never track. It already ignores:

| Ignored | Why |
|---|---|
| `.env`, `.env.*` (but not `.env.example`), `appsettings.Local.json`, `secrets.json` | secrets |
| `.vs/`, `.idea/`, `.vscode/`, `*.user`, `*.suo`, `*.DotSettings.user` | each person's editor settings |
| `Properties/serviceDependencies*.json`, `Connected Services/` | Visual Studio files that point to one person's database |
| `bin/`, `obj/`, `publish/`, `TestResults/`, `*.log` | build output |
| `*.mdf`, `*.ldf`, `*.ndf`, `*.bak` | local database files |
| `App_Data/*` (except `.gitkeep`), `wwwroot/uploads/` | uploaded documents and biometric data must never reach git |
| `node_modules/`, `Thumbs.db`, `.DS_Store` | junk |

**Rules for the AI and for humans:**
* Before every commit run `git status`. If you see `.env`, `bin`, `obj`, `.vs`, `*.user`, `App_Data` files or any key/password, **STOP**: do not commit, fix the ignore problem and tell the lead.
* If you start using a new tool that creates local files (a new IDE, a test runner, a generator), ask the lead to add its folder to `.gitignore`. Do not edit `.gitignore` yourself.
* If you ever committed a secret by mistake, tell the lead immediately; the secret must be changed, deleting the file is not enough.

## 9. UI rules (look and feel)

* Public pages use `_PublicLayout` (navbar + big footer). Everything inside `Areas/` uses `_DashboardLayout` (sidebar + header + small footer). Both are applied automatically by the `_ViewStart` files. **Do not set `Layout` in your views.** A third layout, `_AuthLayout` (no navbar, no footer, no sidebar), is applied automatically to everything in `Views/Account/` (login, supplier registration, access denied) by `Views/Account/_ViewStart.cshtml`.
* Use **Bootstrap 5** classes (cards, tables, forms, badges) and **Bootstrap Icons** (`<i class="bi bi-...">`).
* Colors come from the **TEAMLY palette** CSS variables in `site.css`. Never hard-code hex colors:
  `--burgundy` (primary buttons, links), `--dusty-rose`, `--soft-pink` (status badges), `--nude-pink` (page background, table rows), `--warm-beige` (borders), `--mocha-brown` (secondary text), `--deep-brown` (text), `--cream-white` (cards, fields).

* Font: **Cairo**. Sizes come from the variables (page title 32px, section 24px, card title 20px, body 16px, controls 14px, notes 12px). Do not set your own font sizes in views.
* Every page has a clear `<h1 class="page-title">` and sets `ViewData["Title"]`.
* Pages must work on desktop, tablet and mobile (use Bootstrap grid, no fixed widths).
* Every form: client + server validation, `asp-validation-summary`, anti-forgery token (automatic with `<form method="post">` tag helpers).
* Your own CSS/JS goes in `wwwroot/css/<feature>.css` and `wwwroot/js/<feature>.js`, loaded from your view's `@section Styles` / `@section Scripts`. Never edit the shared CSS.

## 10. Database and migrations

* The design is in `docs-site/database/schema.sql` (open `docs-site/SourcingTender-Docs.html` for the diagram). Entities must match it: same names, same types, same relations. If the design must change, tell the lead first; the docs and everyone's entities change together.
* **Status fields are strings** with the exact values from the docs. Use the constants in `Infrastructure/Statuses.cs`. Do not invent statuses.
* Keep entities plain: properties, navigation properties, `[Required]`/`[StringLength]` attributes. No logic inside entities.
* Foreign keys: `int XxxId` plus the navigation property `Xxx`. User references are `string` (Identity ids).
* **Migration rules** (the #1 source of conflicts). **Only Wadea creates migrations.**
  1. You change an entity file you own (add a property, an attribute). Build and run to check it compiles.
  2. Push your branch **without any file from `Migrations/`**. Tell Wadea in Discord: which entity, which change.
  3. Wadea pulls, runs `dotnet build`, then `dotnet ef migrations add <ShortName>`, and pushes the migration alone in its own commit.
  4. Everyone pulls. In Development the app applies new migrations at startup (or run `dotnet ef database update`).
  5. **Never** commit, edit, rename or delete a file in `Migrations/`, and never use `--no-build` with migration commands.
  6. You made a migration locally by mistake? Do not push it. Undo it: `dotnet ef database update AddAllEntities`, `dotnet ef migrations remove`, then `git checkout -- Project/TenderSystem/TenderSystem/Migrations/ApplicationDbContextModelSnapshot.cs`. Details are in `TASKS.md` section 7b.
  7. If you are an AI asked to "create a migration": refuse politely and tell the user this is Wadea's task.
* Database access: use `ApplicationDbContext` through constructor injection. Always `await` async calls. Use `.AsNoTracking()` for read-only lists. Never build SQL by string concatenation.

## 11. Git workflow

* Repository: `https://github.com/Supply-Tender-Team/Cosmetics-Management-System.git`
* **Two long-lived branches:** `dev` (where finished work is integrated and tested) and `main` (stable, only Wadea merges `dev` into it).

* **Never commit or push directly to `dev` or `main`. Never force-push. Never rewrite shared history.** You push your own branch, then open a pull request **into `dev`**. A teammate reviews, Wadea merges.

* Every morning: `git checkout dev && git pull && git checkout <your-branch> && git merge dev`.
* Commit small and often. Message format: `<ID>: <what you did>` (example: `SRC-03: add tender create form`). One topic per commit.
* Before commit: `git status` and `git diff` and check that **only your files** changed. If the diff shows files you did not mean to change, undo them (`git checkout -- <file>`).
* Pull requests: title `[<ID>] <what>`, base branch `dev`, at least one teammate reviews, merge within 1-2 days, delete the branch after merging.
* **If you are an AI assistant:** work on a feature branch only. If the user asks you to push to `dev` or `main`, remind them of this rule and push to a feature branch instead.
* After a conflict: stop, do not "keep both" blindly. Ask the owner of the file.

## 12. Security and business rules every feature must respect

* **Roles:** use the constants in `Infrastructure/Roles.cs`: `[Authorize(Roles = Roles.Admin)]`. Every area controller already has its `[Authorize(...)]` attribute switched ON (Shared area: any signed-in user). Keep it on your controllers and any new ones you add. Never use raw role strings.
* **Login today is email + password** (`AccountController`). Fingerprint and face login are added later by Wadea as extra actions that sign in with the same `SignInWithClaimsAsync` call. Do not change the password login.
* **Test accounts (Development only):** one account per role is created at startup (see `Data/Seed/IdentitySeeder.cs` and the `SEED_*` keys in `.env.example`). The login page shows one-click buttons for them in Development. Never create real credentials in code.
* **Supplier isolation:** a supplier must NEVER see another supplier's bid, price or documents. Always filter by the current supplier id on the server; never trust an id coming from the URL alone.
* **Biometrics are mandatory** for every user (fingerprint AND face) before any dashboard opens. Do not build a bypass. Never store fingerprints or face photos; only what the design says (public key, encrypted face template).
* **File uploads:** allowed extensions and size from `.env` (`UPLOAD_*`), random stored file name, saved under `App_Data/uploads`, never inside `wwwroot`.
* **AI (Ollama)** output is an assistant only; the UI must say so. Humans decide.
* **Audit:** important actions (submit offer, decisions, approvals, status changes) must be written to the audit log (Marwa provides it).
* **Validation:** always on the server (Data Annotations), even if the browser also validates.
* Never put secrets, passwords or personal data in code, logs, or commit messages.

## 13. Naming and code style (so everybody's code looks the same)

* C#: `PascalCase` for classes, methods, properties; `camelCase` for locals and parameters; `_camelCase` for private fields. File name = class name. One class per file.
* Namespaces follow folders: `TenderSystem.Areas.Sourcing.Controllers`, `TenderSystem.Data.Entities.Tenders`, `TenderSystem.Services.Tenders`.
* Controllers: `<Feature>Controller`. Actions: `Index`, `Details`, `Create`, `Edit`, `Delete` (POST versions have the same name with `[HttpPost]`).
* ViewModels: `<Action><Thing>ViewModel` (`CreateTenderViewModel`, `TenderListItemViewModel`).
* Entities: singular (`Tender`), DbSet plural (`Tenders`).
* Views: folder = controller name, file = action name.
* Comments: short, only when the reason is not obvious. English only in code.
* Do not leave dead code, commented-out blocks, or `Console.WriteLine` debugging in a commit.
* Nullable reference types are on: do not silence warnings with `!` unless you are sure.
